# MalGuard Privacy Policy

## Local scanning and optional network protection

Supported local scanning continues when diagnostics are rejected or unavailable.
Installation diagnostics are separate from optional threat intelligence, update
checks, and scan features that contact cloud services. Diagnostics consent does
not authorize uploading files. See each scanner control's disclosure before
using an online scan feature.

## Explicitly optional installation diagnostics

Diagnostics default to off for new and migrated installations. On first launch,
choose **Allow diagnostics** or **Continue without sharing**. Neither option
changes scanner functionality. No installation diagnostic requests occur before
allowing. The old GitHub launch beacon and compatibility email sender are retired.

Settings → Privacy & Diagnostics shows the random installation ID, last successful
upload, consent state, deletion state, and the registration payload. Preview and
transmission use the same payload builder. A daily heartbeat while the app is
open sends only installation ID, consent, and app version. There is no separate
background tracking service. Disabling sharing stops scheduled uploads and aborts
in-flight client requests; an already received request cannot be recalled.

When enabled and an HTTPS endpoint is configured, registration may include app
version/build, manufacturer/model, CPU model/cores/threads, RAM, GPU model,
Windows edition/version/build, architecture, language, and launch/install outcome.
Unknown information is null or explicitly unknown. Installation success is not
inferred from a launch. Registration time is generated by the server, not claimed
as the installer timestamp. Health-check time remains unknown unless an actual
health check is integrated. Compatibility fields are nullable booleans; no
capability is invented or actively certified just for analytics.

Identity is a random installation UUID, with no linked account or local username.
Detailed hardware descriptions may still be distinctive; this is not a promise
that diagnostic records cannot be reidentified. A separate random credential
stored only on this PC authorizes updates and deletion. It is never included in
the dashboard, preview, or email. The server stores only its one-way hash.

## Optional approximate region

Region sharing is separately off by default. Users may enter a two-letter country
code and province/region. Do not enter an address. There is no automatic IP
geolocation, GPS, coordinate, street, or nearby-network lookup. Clearing region
sharing clears these values on the next registration update and cancels pending
notifications containing the previous region. An already delivered email cannot
be recalled.

## Prohibited data

No diagnostic collector accesses Windows account identity, MAC addresses, network
adapter identifiers, Wi-Fi SSID/BSSID, precise location, passwords, browser
history/cookies/tokens, clipboard, screenshots, camera/microphone, personal
files, credentials, hardware serial numbers, or fingerprint hashes.

Application telemetry handlers do not read, persist, log, email, or display raw
IP addresses. Hosting and email providers necessarily handle network metadata
under their own policies. Infrastructure-level access-log and backup retention
must be reviewed before enabling a deployment; this source cannot promise what
a hosting provider retains outside the application.

## Administrator access and email

Only an authenticated administrator can read the dashboard/API. When configured,
a separate server worker may email the administrator once for a consented
registration. Email contains only the disclosed registration fields. Retried
requests use one event ID; retries end before the provider's idempotency window
expires. Email failures do not affect registration, installation, or scanning.

## Disable, delete, and retention

Turning diagnostics off also requests deletion. This explicit privacy-control
request carries only the installation ID and deletion authorization, not device
diagnostics. Deletion removes the installation, capability record, and associated
email-event record; it stops future client uploads. If offline, local sharing is
still disabled and deletion is shown as pending. Retry manually when online.
The application does not falsely claim remote deletion or silently retry uploads.

After successful deletion, the client discards its old credential and creates a
new random ID. It never reconstructs identity from hardware. A server tombstone
containing only the deleted random ID rejects delayed registration replays for
30 days, then is removed. Lost credentials cannot be recovered through a hardware
fingerprint. A registration already in flight may race deletion; database locks
serialize registration/update/deletion for the same ID.

The maintenance job removes installation records after 90 days without an
accepted update. Capability and notification records cascade with deletion.
Notification payloads are cleared after seven days once sent or permanently
failed. Minimal event status remains only while the installation exists to
prevent duplicate emails. No indefinite soft-deleted installation records exist.
The operator must schedule maintenance; retention is not enforced by a dormant
serverless function. Backups must expire within 30 days, and administrator
notification emails must be deleted within 30 days. Those provider/mailbox
policies are deployment requirements, not controls this source can enforce.
Deletion cannot retract already delivered email or an email request in flight.

## Deployment status

This feature is disabled server-side unless explicitly configured and needs a
reviewed database migration, endpoint configuration, and maintenance schedule.
Source implementation does not mean production telemetry has been enabled.
